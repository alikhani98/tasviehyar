# ALPHA-01 — P0 architecture audit: local-first and dual backup

**Repository:** `alikhani98/tasviehyar` · **Target origin:** `https://hesab.54i.ir` · **Audit date:** 2026-11-08 (Asia/Tehran)

**Reviewed checkout:** `redesign/mobile-tablet-v1`, `ed6e32f1489fd5a599095d6360df3ba28332fa8f`, app `0.9.0-alpha.0`. The existing untracked production ZIP was left untouched; this is a source audit, with no assertion that the deployed artifact matches the checkout.

**Decision:** Keep the single-user static frontend, existing HTTPS origin, IndexedDB/Dexie as the source of truth, schema **3**, and downloadable JSON backup format **1**. Local export covers all financial stores, but it does not guarantee a consistent snapshot under concurrent writes. Restore replaces the eight stores atomically; the UI can still report failure after a successful commit. Approve local backup hardening and staging verification before enabling an optional browser-encrypted private copy on DirectAdmin. No permanent Node service, MariaDB, synchronization, or financial-domain changes are needed.

**Evidence labels:** **VERIFIED** means observed in the reviewed source or an executed check, as specified. **INFERRED** identifies a consequence of the design or an untested condition. **UNKNOWN** identifies evidence unavailable in this audit. Design recommendations describe future work.

All stores use `id` as their primary key; no other store or explicit upgrade handler is declared in this class. Every store is included in export, preview counts, and replace-all restore. See [database definition](../src/db/tasviehyar-db.ts#L13) and [backup service](../src/services/backup-service.ts#L210).

**VERIFIED — source.** The backup captures records, including lifecycle states and audit events. It excludes theme and the last 20 backup/restore entries in `localStorage`, browser state, Cache Storage, and any external file referred to by a string such as `paperInvoiceImageRef`. These are separate from financial store coverage. The [business date helper](../src/domain/business-date.ts#L1) uses Asia/Tehran. Backup envelope timestamps default to UTC ISO strings; download filenames use device-local calendar and minute fields. Neither sets the financial business date.

**VERIFIED — source and installed dependency tree.** Backup uses Zod 4.6.7, Dexie 4.4.4, UTF-8 via `TextEncoder`, browser Web Crypto SHA-256, and standard file/Blob APIs. No dedicated backup encryption, compression, or remote transport is implemented. ExcelJS 4.4.0 brings JSZip 3.10.1 and pako 1.0.11 transitively; neither is used by backup. `fake-indexeddb` is used for test setup, not app persistence.

## 2. Verified backup and restore capabilities

- **Complete store coverage; snapshot consistency missing. VERIFIED.** Export issues eight separate `toArray()` calls using `Promise.all`, without a shared read transaction. It builds an envelope with app ID `tasviehyar`, format 1, schema 3, optional application version, creation time, eight counts and eight record arrays. It returns pretty-printed plaintext JSON even when its domain integrity preview has blocking issues. An isolated forced interleaving returned a backup containing an invoice whose newly created party was absent, and reinspection rejected it.
- **Compatibility validated. VERIFIED.** Restore requires exact app ID, format **1** and schema **3**, plus the expected envelope and record shape. The optional application version is informational; there is no upgrade or downgrade conversion. Do not infer schema-2 compatibility from the fact that the file is JSON.
- **Corruption checks run before writes. VERIFIED.** Malformed JSON, invalid Zod shape, mismatched counts, stale checksum and selected graph violations block restore. Checks cover duplicate IDs in each store, missing references, destination-account ownership, several allocation relationships, safe nonnegative integer amounts, total allocation per payment and active instruction total per invoice. Duplicate tracking references and probable duplicate records are warnings. This is a set of checks, not a replay of repository operations or an audit chain; e.g. the audit check requires a nonblank description but does not prove that all events exist. See [validation](../src/domain/backup.ts#L239).
- **Checksum verified; authenticity absent. VERIFIED.** The client compares SHA-256 over UTF-8 `JSON.stringify` of a reconstructed unsigned envelope after schema parsing, rather than hashing the uploaded bytes verbatim. Whitespace is immaterial. Fields stripped or defaulted by schemas are not protected as raw file contents, and normalized field ordering matters to compatibility. The hash is unkeyed. The probe confirmed that a changed party name and removed audit array passed after counts and checksum were recomputed.
- **Atomic financial restore. VERIFIED.** After inspection, all eight clears and all eight `bulkPut` calls are awaited inside a single Dexie `rw` transaction. Rejected writes propagate out of it; the existing injected audit-write failure test verified byte-equivalent prior export and no restore history entry. No committed subset of the eight stores is expected on transaction failure under the [IndexedDB transaction model](https://www.w3.org/TR/IndexedDB-3/#transactions). This is not proof against device loss or OS power failure; real-browser quota and interruption cases were not exercised.
- **Restore completion is separate from commit. VERIFIED.** After commit the service revalidates the in-memory incoming bundle (not database readback), then writes history to `localStorage`. A quota error caused the restore promise to reject while the replacement rows and audit event were committed. The UI success notice and data refresh event occur only after the service returns, so a committed restore can appear to have failed. A storage write error also stopped export from returning its already constructed file. See [commit and history boundary](../src/services/backup-service.ts#L400).
- **Persian backup UI. VERIFIED — source and mock UI tests.** The lazy backup screen offers a normal download, isolated synthetic demo download, JSON file picker, counts, compatibility preview and warnings, and a confirmation before replacement. It blocks repeated submission in the mounted screen. It warns about sensitive files and recommends a fresh backup before restore; no fresh checkpoint is enforced. It records export history before the browser download is attempted, and its anchor click does not prove the file was saved. See [BackupRestore](../src/features/backup-restore/BackupRestore.tsx#L129).

## 3. Security weaknesses and failure scenarios

| Scenario | Evidence and impact |
| --- | --- |
| Concurrent financial write during export | **VERIFIED** with a forced interleaving: separate reads produced an unrestorable file. **INFERRED:** another interleaving could produce a valid-looking but incomplete cut that passes graph checks. |
| Damaged, truncated or incompatible file | **VERIFIED** that parse, version, count, hash and domain failures are checked before the write transaction. A modified file with a valid recomputed hash can pass. The v1 checksum must never be presented as a signature. |
| Very large or hostile JSON | **VERIFIED** the UI reads the whole file without an explicit size cap; parse, lookup construction and validation happen before commit. **INFERRED** memory pressure, long UI stalls, or failure before any write on a low-memory device. Several validation loops scan dependent arrays repeatedly. |
| Storage fills during restore | **VERIFIED** rollback for an injected write error. **UNKNOWN** browser-specific behavior under real quota/termination. **VERIFIED** separately that quota failure in backup history can misreport a committed restore. |
| Older, empty, or demo snapshot chosen by mistake | **VERIFIED** replace-all, including audit events. Empty v1 snapshots are valid, and there is no mandatory pre-restore copy. **INFERRED** newer records and events may be lost without a retained checkpoint. There is no automatic merge or undo. |
| Overlapping tabs or file selections | **VERIFIED** the in-flight UI guard is component-local and there is no restore freshness token. File inspection is asynchronous without a latest-selection guard. **INFERRED** a later-finishing inspection may replace the intended preview; another tab can commit changes before a restore replaces them. Database atomicity does not prevent either problem. |
| Lost device, cleared browser data, or plaintext backup disclosure | **VERIFIED** local JSON can contain names, phone numbers, bank identifiers, payments and notes in cleartext. **INFERRED** a copy left in Downloads or automatic device sync can leak those fields. Browser storage is scoped to the origin/profile and can be evicted or cleared; an external copy is required for recovery. [Browser quota and eviction reference](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). |

## 4. Service Worker v4 and production constraints

**VERIFIED — source.** [Service Worker v4](../public/sw.js#L2) precaches the root, index, manifest, SVG and two PNG icons. It registers at `/sw.js`, skips waiting and claims clients. Activation deletes every other Cache Storage name visible to that origin; it does not touch IndexedDB. Same-origin GETs are intercepted except when the URL pathname ends in `.json`. Navigations use network first, save a successful response under `/index.html`, and fall back to cached index/root or 503 when the network path throws. Non-navigation requests are cache-first, and successful network responses are cached without inspecting cache headers. Hashed JS/CSS and lazy chunks are not explicitly precached, so a feature never loaded online may be unavailable offline. A resolved HTTP error is not the same as a network failure for the navigation fallback.

**VERIFIED — VM probe.** With the checked-in worker and mocked Cache Storage, an extensionless same-origin GET marked `Cache-Control: no-store` was replayed offline, whereas `.json` GET and POST bypassed the handler. **INFERRED** that a plain `/api/backups` or `/backup.php` list/download URL could leave cached responses after sign-out and may show a stale list. A top-level navigation to a cacheable endpoint also risks polluting the app shell fallback. Cache Storage does not apply HTTP cache policy on behalf of app code. [Cache API reference](https://developer.mozilla.org/en-US/docs/Web/API/Cache).

**Recommended v4-compatible route:** expose only `/api/backup-v1.json`, internally route to PHP on the same origin, and keep the external path ending in `.json` for every operation. Return no external redirects, including on auth failure. Exclude the path from SPA fallback and proxy/CDN caches; return `Cache-Control: no-store` on success and errors and request `cache: "no-store"` from the client. Verify routing and bypass in real controlled browsers. If hosting cannot implement that mapping, request a narrowly scoped API bypass in the worker and separately approve the cache/version and rollout implications. Do not ship the API on a path v4 intercepts.

**UNKNOWN — production.** The public browser fetch could not access the URL and the shell HEAD request failed DNS resolution in this environment. Neither establishes a production outage. Current TLS, active artifact and worker, effective docroot, PHP version/handler, server stack, rewrites, response headers, account and temporary storage quotas, process identity, `open_basedir`, vhost aliases, cron access, hosting backup policy, and outbound/offline device behavior were not verified. [Release runbook](phase-5-release-hardening.md#directadmin) describes the intended deployment; DirectAdmin documents [PHP configuration differences](https://docs.directadmin.com/webservices/php/php-options.html) and [subdomain document-root configuration](https://docs.directadmin.com/webservices/php/multiple-php.html). Verify effective settings on staging with the actual hosting account. No public diagnostic script is required.

## 5. Proposed dual backup and key management

1. **Local copy:** take one readonly Dexie transaction covering all eight stores. Complete the read, then serialize/hash outside the transaction. Run the same import inspection before presenting the snapshot as usable. Keep the current downloadable v1 JSON unchanged. Separate export generation from optional history and describe the download as started; provide simple instructions to retain it on a separate protected device or volume.
2. **Private copy:** when the operator chooses server backup, encrypt the exact validated v1 JSON bytes from the same snapshot in the browser. Wrap them in a separately versioned encrypted container, never a new inner format. Use browser Web Crypto AES-256-GCM with a fresh random 96-bit nonce for each encryption and a 128-bit tag. Define and authenticate a bounded, deterministic header as additional authenticated data (container version, fixed algorithm/profile and nonsecret key ID); use a binary frame to avoid base64 overhead. Reject unknown profiles, invalid lengths, failed authentication, and oversize input before parsing or restoring. No compression in ALPHA; if justified later, compress before encryption under a new supported profile and cap decompressed size. [Web Cryptography specification](https://www.w3.org/TR/webcrypto/).
3. **Recovery key:** generate a high-entropy 256-bit recovery secret in the browser. Display/export it once with a clear key ID and require a recovery drill with a clean profile. Keep it in an independent password manager or separately secured offline recovery media. Import a nonextractable CryptoKey for the session, drop app references on lock/close, and never transmit or persist the secret in PHP, logs, browser storage, URLs or alongside ciphertext. Store only the public key ID in the encrypted container. Use a different credential for PHP access. Rotation creates a new key ID; keep old keys until all corresponding snapshots expire and recovery is verified. Losing the secret makes those encrypted copies unrecoverable; the separate local copy still works. Keep passphrase-derived keys out of the first release to avoid weak human secrets and untested KDF choices.
4. **Recovery:** fetch opaque bytes after authorization, decrypt in the browser, then run the existing v1 validation and show the same counts and replacement preview. Require explicit confirmation and a verified, accessible pre-restore checkpoint for a nonempty database; local checkpointing must work without the server. Check for intervening writes across cooperating tabs, and distinguish a committed restore from a history error. Do not silently discard newer audit events: preserve them in the checkpoint, show the replacement boundary, and record the restore result. No background or automatic restore.
5. **Outage:** network calls are optional, time bounded and independent of local work. Keep normal financial work and local export/import available offline once the needed app assets are cached. Show separate local/server results and the last **confirmed** server save; on timeout after upload, show an unknown result and reconcile by idempotency ID or allow explicit retry with the same ciphertext. Never send plaintext as a fallback or start a new backup on every write. A known unavailable server blocks only remote operations; a device with no usable local copy must wait for access to the remote copy.

**Threat boundary:** client encryption protects against theft of stored blobs and host backups if the key stays separate. The server still sees timing, sizes and access metadata. A compromised same-origin frontend or service worker can read live IndexedDB, capture an entered key, or act with the session; encryption cannot fix that. Restrict deployment credentials and vhost isolation, review the frontend supply chain and response security headers, and keep an independently verifiable local recovery copy. A compromised storage account may withhold, replay or delete entire valid snapshots; encryption alone does not prove freshness or availability.

## 6. Minimal DirectAdmin PHP API

**INFERRED — feasible if staging gates pass.** One PHP handler with static frontend assets; no persistent process or database. Use method and action allowlists, a separately provisioned single operator credential and a short-lived PHP session. Store the credential verifier and session state privately, using PHP password hashing/verification and session ID rotation on login. Scope a host-only Secure, HttpOnly, SameSite=Strict cookie to the API path. Require authorization on every data action; require the expected Origin and a session CSRF token on authenticated mutations, and apply a same-origin check, rate limit and no cross-origin access to login. Disable CORS, reject unsupported methods, bound sessions and protect login against guessing. The app shell must continue to open without a backup session. [OWASP file upload controls](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

| Operation | Contract |
| --- | --- |
| Upload: `POST ?action=upload` | One bounded encrypted blob; ignore user filename. Validate upload status, size and container framing only. Generate a random storage ID server-side. Use a random private stage file, check quotas under a lock, and publish with a same-filesystem atomic rename on the verified host. A bounded operation ID and digest allow safe retries; never overwrite an existing object. Return success only after publication. |
| List: `GET ?action=list` | Return bounded, paged metadata (opaque ID, received time, ciphertext size, optional pin state) for committed entries. No party data, original file names, filesystem paths or ciphertext in list responses. Derive metadata from committed objects or reconcile it under the same lock; avoid a separately published manifest that can drift. |
| Download: `GET ?action=download&id=…` | Authenticate, resolve a strictly validated ID beneath the private root and stream as an attachment with `application/octet-stream`, `nosniff` and `no-store`. Authorize each request; no static or bearer download URLs. Only the browser can authenticate/decrypt the content. |
| Delete: `POST ?action=delete` | Require CSRF, explicit operator confirmation and fresh authorization. Mark retired or move to private trash under the same lock; protect pinned and last known recoverable copies. Record minimal security and retention events. No deletion of IndexedDB records. Enable permanent purge only after policy approval and staging recovery drills. |

Place blobs, stage files, sessions and credentials outside **all** web roots and aliases, accessible only to the account/PHP identity (e.g. owner-only directory and file modes where supported). Do not serve or execute uploaded content. Reject user paths and symlinks, use a fixed private root, bounded streams and sanitized logs, and set matching proxy/PHP request and upload limits with room for multipart framing. Test effective limits and `open_basedir`, quotas, locking and filesystem behavior. Account for PHP's temporary copy and staging overhead; rate limit before PHP when possible. Detect abandoned staging files and crash outcomes; atomic publication does not guarantee survival of a host power loss. Use structured failures (e.g. 401/403, 413, 429, capacity/unavailable) and verify PHP/wrapper changes leave static routing intact. PHP documents [upload configuration](https://www.php.net/manual/en/ini.core.php) and [upload provenance checks](https://www.php.net/manual/en/function.move-uploaded-file.php); the latter does not provide a no-overwrite guarantee.

## 7. Retention proposal

Start manually: operator creates a server copy after each working day with financial changes and before release/restore. Keep the latest **7 distinct daily** snapshots plus **4 weekly** and **3 monthly** snapshots, deduplicating overlaps, with independently pinned pre-restore and release checkpoints. Treat these as proposed recovery targets; size and count limits must follow staging measurements and available disk. Define retention dates in Asia/Tehran using server-assigned receipt timestamps for grouping; leave finance dates untouched. Propose a 14-day private trash window for explicit deletion and a monthly decrypt/restore drill in an isolated profile. Keep at least one independently verified local copy outside the host.

Never silently prune the last known-good copy to accept an upload; at capacity return a clear failure, preserve existing snapshots and prompt the operator to review retention. Initially review retirement manually. Before automating purge, confirm pin/trash rules, host backup retention and whether removed files persist in provider backups. Keep operational logs minimal and bounded; exclude content, credentials and keys. Final retention and quotas remain **UNKNOWN** pending operator and hosting review.

## 9. Migration and compatibility risks

- Preserve the exact HTTPS origin (scheme, hostname and port) and database name. An origin change or different browser profile can present an empty database; a redirect cannot move origin-scoped IndexedDB. The PHP feature is additive and does not require a data migration. [Origin isolation reference](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy).
- Do not change Dexie schema 3, inner backup format 1, or its checksum reconstruction as part of this work. Capture existing v1 fixtures with optional fields and audit history; pin compatibility through restore and re-export. The encrypted wrapper is a separately versioned transport/storage format. Older app builds can still read plain v1 JSON; they cannot read the wrapper. Keep a tested recovery path for retained wrapper versions and historical keys.
- Restoring an earlier snapshot can replace newer financial and audit rows. Treat restore as explicit recovery with a separately retained checkpoint. Leave the settlement, allocation and Tehran business-date logic untouched. Keep old frontend artifacts and required hashed chunks available for a controlled same-origin rollback. Disable the optional server feature on rollback without purging data, rotating keys, or clearing browser storage.

## 10. Prioritized implementation proposal for ALPHA approval

1. **P0 — approve local hardening first.** Use one all-store read transaction, require import-valid export, bound import size, separate history failures from file/restore outcomes, and protect replace-all with a verified checkpoint and freshness controls. Gate on v1 fixtures, financial/audit regression tests, and a real-browser restore drill.
2. **P0 — approve staging feasibility checks in parallel with local hardening.** Confirm same-origin PHP routing via the v4-exempt path, HTTPS, isolated writable storage, limits, private access controls, and usable device recovery. If any gate fails, retain local-only backup. Seek separate approval for a worker change only if safe routing cannot be achieved with v4.
3. **P1 — approve a manual, opt-in encrypted server pilot after both P0 gates.** Implement browser encryption and key recovery, PHP upload/list/download, and separate local/server status. Require independent local copy, clean-profile recovery, and a failure drill before live financial use. Keep deletion disabled until the recovery drill passes.
4. **P2 — approve retirement and purge separately.** Enable explicit, recoverable retirement, then consider scheduled purge only after the operator confirms retention, quotas, provider backup behavior and recovery evidence. Preserve the existing origin and every protected contract throughout.
